## 一、Agentic RAG 状态图（app/rag/）

这是整个项目的**心脏**：用 LangGraph 的 `StateGraph` 把问答流程编排成一张
可回退、可重试、路径确定的状态机。9 个节点、4 组条件路由。

### 1.1 `app/rag/graph.py` —— 图怎么接

| 定义 | 行号 | 作用 |
|---|---:|---|
| `STEP_LABELS` | 48 | 节点名 → 中文展示名（流式进度、CLI 轨迹共用） |
| `required_recursion_limit()` | 61 | 按当前配置估算图最多跑几步，兜底 recursion_limit |
| `build_graph()` | 72 | **把节点和边接起来 —— 想看全图就看这个函数** |

9 个节点：`route_question → transform_query → retrieve → rerank_documents →
grade_document → (rewrite_query / web_search) → generate → check_groundedness`。

### 1.2 `app/rag/edges.py` —— 条件路由（纯函数，不调 LLM）

| 函数 | 行号 | 决策逻辑 |
|---|---:|---|
| `decide_after_route` | 13 | 需要实时信息 → 联网；否则先查本地 |
| `decide_after_grading` | 18 | 有相关文档→生成；无相关&可改写→改写；无相关&额度尽→联网或兜底 |
| `decide_after_rewrite` | 40 | 改写有效→回 transform_query；无效→联网或兜底 |
| `decide_after_groundedness` | 51 | 未通过且有额度→回 generate 严格重生成；否则结束 |

这正是"确定性 Agentic 流程"的含义：LLM 只负责判断（评分、路由），走哪条路由代码说了算。

### 1.3 `app/rag/state.py` —— 共享状态 `GraphState`

`GraphState` 是 `TypedDict`，运行时就是普通 dict。字段分五组：问题、记忆、路由与联网、
检索、生成与忠实性。**读它的注释能理解整张图。**

> 节点函数约定：接完整 state，**只返回要更新的字段**，LangGraph 自动合并。
> 所以"改了却没 return"的修改会被丢弃。

### 1.4 `app/rag/nodes/` —— 节点实现

| 文件 | 节点 | 做什么 |
|---|---|---|
| `route.py` | `route_question` | 补全追问 + 判断先查本地还是直接联网（尽量零 LLM 调用） |
| `retrieval.py` | `transform_query` | 查询变换：none / multi_query（RAG-Fusion）/ hyde |
| `retrieval.py` | `retrieve` | 混合检索（调 `vector_store.amulti_query_search`） |
| `retrieval.py` | `rerank_documents` | Cohere 交叉编码精排（失败降级透传） |
| `retrieval.py` | `grade_documents` | LLM 逐条评分过滤无关文档（并发执行） |
| `retrieval.py` | `rewrite_query` | 改写查询后重新检索 |
| `web.py` | `web_search` | Tavily 联网搜索，结果转为 Document |
| `generation.py` | `generate` | 按资料生成答案（本地/网页/严格三套提示词） |
| `generation.py` | `check_groundedness` | 忠实性自检 + 触发严格模式重生成 |

### 1.5 `app/rag/prompts.py` —— 全部提示词

集中放提示词模板与兜底文案，每个模板上方注明它被哪个节点使用：

| 提示词 | 用途 |
|---|---|
| `ROUTE_PROMPT` | 入口路由（补全 + 选数据源，两件事一次 LLM 调用） |
| `MULTI_QUERY_PROMPT` / `HYDE_PROMPT` | 查询裂变 / 假想答案 |
| `DOC_GRADE_PROMPT` | 文档相关性评分 |
| `REWRITE_PROMPT` | 查询改写 |
| `GENERATE_PROMPT` / `WEB_GENERATE_PROMPT` / `GENERATE_STRICT_PROMPT` | 本地/网页/严格三套生成 |
| `GROUNDEDNESS_PROMPT` | 忠实性检查（含中英数字换算表，防误判） |
| `CONVERSATION_RULES` | 对话背景与资料的隔离规则 |
| `FALLBACK_ANSWER` / `WEB_FALLBACK_ANSWER` | 兜底拒答话术 |

### 1.6 `app/rag/helpers.py` —— 节点共用的纯函数

解析 LLM 输出（`parse_yes_no` / `parse_query_list` / `parse_route` / `normalize_question`）、
拼上下文（`format_context`）、联网判定（`web_allowed` / `can_web_search` / `local_rewrite_budget`）、
流式写入（`stream_writer`）。**都不调 LLM、不访问外部服务，可直接单测。**

### 1.7 `app/rag/llm.py` —— LLM 与精排器

| 函数 | 行号 | 作用 |
|---|---:|---|
| `get_llm(**kwargs)` | 17 | 统一创建智谱 GLM 客户端（走 OpenAI 兼容协议，挂 Redis 缓存） |
| `get_reranker()` | 35 | Cohere Rerank 精排器（未配置/失败时返回 None） |

### 1.8 `app/rag/chain.py` —— 对外封装 `RAGChain`

调用方（FastAPI、CLI、RAGAs 评估）只和这个类打交道：

| 方法 | 行号 | 作用 |
|---|---:|---|
| `_initial_state()` | 86 | 一次请求的初始状态（每个字段显式给出，避免读到残留值） |
| `aanswer()` | 121 | 一次性返回答案 |
| `astream_events()` | 144 | 流式执行，逐个产出 step/token/reset/done 事件 |
| `_build_payload()` | 216 | 把最终状态整理成答案 + 来源 + 观测字段 |

**关键设计**：`aanswer` 内部就是把 `astream_events` 跑完取最后的 done 事件 ——
流式和非流式只有一条代码路径。记忆加载/写回/压缩也在这里完成。

## 二、检索层（app/retrieval/ + app/vector_store.py 门面）

### 2.1 五个模块各自负责什么

| 文件 | 内容 |
|---|---|
| `embeddings.py` | 本地 Embedding 模型（BGE，`get_embeddings()` 单例，含下载失败中文诊断） |
| `milvus.py` | Milvus 连接、打开失败中文诊断、实体计数、维度检查 |
| `corpus.py` | BM25 语料副本（JSONL）—— Milvus 只存向量，BM25 需要原文，重启后据此重建倒排索引 |
| `bm25.py` | 中文分词（jieba，退化为字+二元组）+ BM25 倒排索引缓存 |
| `fusion.py` | RRF 融合与跨通路去重 |
| `search.py` | 稠密/稀疏/混合/多查询检索入口 |
| `store.py` | 入库、按文档删除、清库、预热、统计 |

### 2.2 `app/vector_store.py` —— 门面

对外统一暴露检索层能力，并加一层**异步版本**（`amulti_query_search` 等），
把同步的 Milvus/Embedding/BM25 调用移到工作线程，不阻塞事件循环。
RAG 节点和文档管理都通过它调用，测试只需在这里 patch 一处。

### 2.3 混合检索 + RRF

```
               ┌─ 稠密：Milvus 向量检索 (Top 20) ─┐
 查询 ─────────┤                                   ├─ RRF 融合 ─► Top 20 ─► Rerank ─► Top 5
               └─ 稀疏：BM25 关键词检索 (Top 20) ─┘
```

- **稠密**负责"语义相近"；**稀疏**负责"关键词精确命中"（专有名词、型号、人名）。
- **RRF**：`score = Σ weight_i × 1/(60 + rank_i)`。稠密余弦(0~1)和 BM25(无上界)量纲不同，
  直接加权没意义，RRF 只看排名，天然免疫量纲问题。
- **去重键** `_doc_key` = `source|md5(内容)`：不用 Milvus 主键 `pk`，因为 BM25 那路没有 pk，
  否则同一块会被当成两个结果（`fusion.py` 有踩坑记录）。
- **多查询融合** `multi_query_search`：N 条查询各做一次混合检索，再统一 RRF。

## 三、一次 `/query` 的完整旅程

假设问 **"Llama 2 的参数量是多少？"**：

```
【1】app/api/routes/query.py:29  query()
      │  收到 JSON，Pydantic 校验 → 调 RAGChain.aanswer()
      ▼
【2】app/rag/chain.py:121  aanswer() → astream_events()
      │  加载会话记忆（有 session_id 时）→ 填初始 GraphState → 交给状态图
      ▼
【3】app/rag/nodes/route.py  route_question
      │  有历史则补全追问；WEB_ROUTING=llm 时判断是否依赖实时信息
      │  本例判 local → 走本地检索
      ▼
【4】app/rag/nodes/retrieval.py  transform_query
      │  QUERY_TRANSFORM=multi_query → LLM 裂变出 3 条查询，加上原问题共 4 条
      ▼
【5】app/rag/nodes/retrieval.py  retrieve
      │  调 vector_store.amulti_query_search()
      │    每条查询 → 稠密(Top20) + 稀疏(Top20) → RRF 融合
      │    4 条查询的结果再 RRF 融合一次 → Top20 候选
      ▼
【6】app/rag/nodes/retrieval.py  rerank_documents
      │  Cohere 交叉编码把 [问题+每篇] 拼起来重打分 → 留 Top5
      │  （Cohere 挂了就透传原候选）
      ▼
【7】app/rag/nodes/retrieval.py  grade_documents
      │  LLM 逐条判断"这段能回答吗"，并发执行，过滤无关的
      ▼
【8】app/rag/edges.py  decide_after_grading
      │  有相关文档 → generate
      │  全不相关   → rewrite_query 改写后回 transform_query（受预算限制）
      │              或额度用尽 → web_search 联网（CRAG 纠错）
      ▼
【9】app/rag/nodes/generation.py  generate
      │  把文档拼成【资料】+ 对话背景拼成【对话背景】→ GLM 生成答案（流式）
      ▼
【10】app/rag/nodes/generation.py  check_groundedness
      │  让 GLM 当裁判：答案每句话都能在文档里找到依据吗？
      │  ├─ 通过 → 结束
      │  └─ 不通过 → strict_grounding=True → 回 generate 严格重生成一次
      ▼
【11】app/rag/chain.py  _build_payload()
      │  把 Document 转成 sources（含 relevance_score / rrf_score / doc_id）
      ▼
【12】返回 QueryResponse：answer + sources + queries + groundedness + steps + …
```

**读代码时对着这条链路走一遍，每个函数的输入输出就都清楚了。**

## 四、上下文工程与会话记忆

### 4.1 `app/context.py` —— 放什么、放多少、怎么放

| 动作 | 做法 |
|---|---|
| 选择 | 只注入最近 `HISTORY_TURNS` 轮 + 滚动摘要；资料按相关度取前若干条 |
| 压缩 | 历史受 `MEMORY_CONTEXT_CHARS` 预算，资料受 `CONTEXT_MAX_CHARS` 预算（`fit_documents`） |
| 隔离 | 历史放【对话背景】区，资料放【资料】区，新事实必须来自资料 |

### 4.2 `app/memory.py` —— 存什么、怎么压、存哪

- **存什么**：`summary`（滚动摘要）+ `turns`（最近 N 轮原文）。问题存**补全后的独立问题**。
- **怎么压**：超过 `MEMORY_WINDOW_TURNS` 轮时，把较早轮次 + 旧摘要交给 LLM 合并成新摘要，
  只留最近 `MEMORY_KEEP_TURNS` 轮。批量压缩，约每 4 轮才调一次摘要。
- **存哪**：`MEMORY_BACKEND` 选 sqlite（默认）/ redis / memory / off。
- **为什么不直接用 LangGraph checkpointer**：它每超步都存完整图状态（含文档列表），太重。

## 五、文档管理（app/documents.py）

每个文件是一条登记记录（SQLite），每个 chunk 的 metadata 都带 `doc_id`：

| 能力 | 实现 |
|---|---|
| 内容去重 | `doc_id = SHA-256(内容) 前 16 位`，换名重传也认得出 |
| 版本替换 | `source_key` 相同但内容变了 = 新版本，入库成功后才删旧版本 |
| 后台入库 | 单工作协程串行（Milvus Lite 单写 + Embedding CPU 密集），上传立即返回 202 |
| 重启恢复 | 未完成（pending/processing）任务自动重新排队 |

状态流转：`pending → processing → ready`（失败则 `failed`）。

## 八、命令行会话层（research_agent/）

`research_agent/agent.py` 提供 CLI 多轮对话，与 HTTP 接口**共用同一张状态图和同一个记忆库**。
它只多做三件事：管理 thread_id（即 session_id，固定默认值所以重启接上上次对话）、
懒加载 RAGChain、把执行路径整理成可读轨迹。所有检索/联网/生成/记忆逻辑都在 `app/` 里。
