# Agent 开发岗位申请材料：RAG_mine

> 项目定位：一个可运行、可观测、可降级的 Agentic RAG 文档问答服务。系统用 LangGraph 把
> 检索、联网、生成、忠实性自检编排成一条**路径确定**的状态机（Corrective RAG），
> 本地知识库查不到相关内容时自动降级为联网搜索。

本项目独立开发 Agentic RAG 研究助手：以 LangGraph 编排可控的检索/反思流程，以 Corrective RAG 的
条件路由替代开放式 ReAct 循环，实现混合检索、查询变换、精排、联网纠错、工具容错、异步化、
LLM 缓存、可观测性及自动化验证。

## 二、使用的原生 API 与 Agent SDK

本项目使用 **LangChain + LangGraph** 搭建，通过 **OpenAI 兼容 API** 调用智谱 GLM。
依赖约束以仓库中的 `requirements.txt` 为准。

| API / SDK | 项目中的用途 | 能力边界 |
|---|---|---|
| LangGraph `StateGraph` | 编排 9 节点 RAG 状态图；条件边决定路由；`recursion_limit` 兜底 | 提供节点调度、状态合并、条件边和递归上限机制 |
| LangChain `ChatOpenAI` | 统一创建模型客户端；查询变换、评分、生成、忠实性判断 | 提供消息组装、流式输出和模型调用协议 |
| 智谱 GLM OpenAI 兼容 API | 查询变换、相关性评分、答案生成、忠实性判断、入口路由 | 提供模型推理；模型与地址由环境变量配置 |
| Tavily Search API | 状态图中的联网搜索节点 | 提供实时网页检索结果 |
| Cohere Rerank API | 对混合召回候选做交叉编码精排 | 可选增强项；未配置或失败时透传原候选 |
| Hugging Face 本地 Embedding + Milvus | 文本向量化、存储和稠密召回 | Embedding 本地运行；Milvus 默认 Lite 文件模式 |
| Redis / Prometheus | LLM 响应缓存；接口 QPS、延迟、状态码和在途请求指标 | 工程基础设施，不参与 Agent 决策 |

关键选型考虑：

- OpenAI 兼容协议降低模型供应商耦合，HTTP 服务与 CLI 共用同一组模型配置。
- 固定流程用 `StateGraph` + 条件边表达，不套 ReAct Agent——联网时机只有两种确定情况，
  用 LLM 每轮推理"要不要调工具"既慢又不稳定。
- 本地 Embedding 降低高频向量化的调用成本；Milvus Lite 便于本地演示，也可通过 URI 切换服务端。
- Cohere、Tavily、Redis 都按"增强能力"设计，单项故障不会直接拖垮核心问答链路。

## 三、Agent Loop 与工具调用如何实现

### 3.1 状态图：一条路径确定的状态机

`app/rag/` 用 `GraphState(TypedDict)` 在节点间传递问题、候选文档、重试次数、生成结果和忠实性状态。
主流程（`app/rag/graph.py`）：

```text
route_question ──(需要实时信息)──────────────────────────► web_search ─┐
     │                                                       ▲         │
     └─(local)→ transform → retrieve → rerank → grade ─(无相关文档)─┘    │
                                                    │                     ▼
                                                    └─(有相关文档)──► generate → check_groundedness
                                                                           │
                                          (未通过且有额度)──严格重生成◄─────┘
```

这张图有两种自我修正：

1. **检索回环**：本地检索评分后没有相关文档时，改写查询重新检索（`MAX_RETRIES` 限制）；
   联网可用时则直接转联网（Corrective RAG 的纠错分支）。
2. **生成回环**：答案未通过忠实性检查时，用更严格的提示词重新生成（`MAX_GROUNDEDNESS_RETRIES` 限制）。

`required_recursion_limit()` 按配置估算最大步数并兜底，防止错误路由造成无限循环。每个节点只返回
需要更新的字段，由 LangGraph 合并状态，使路径和副作用都能单独观察。

### 3.2 联网搜索：状态图中的节点，而非 Agent 工具

需要联网的情况只有两种，而且都是确定的：

- 问题依赖实时信息（新闻、价格、天气……）—— 入口 `route_question` 判断一次；
- 本地检索 + 精排 + 评分之后没有相关文档 —— 纯规则判断。

这正是 Corrective RAG（CRAG）的做法：联网是检索失败后的纠错分支，用条件边表达即可。相比
ReAct Agent，路径确定、LLM 调用次数有上限、可单测，出处不会被外层 LLM 再改写一遍。

### 3.3 工具可靠性与会话设计

- **懒加载与隔离**：本地 RAG、Tavily 客户端都懒加载。只联网时不会预先加载 Embedding；
  本地库初始化失败不阻止服务启动。
- **参数防御**：联网结果条数被夹在 `[1, 10]`，网页正文按字符数截断，避免上下文膨胀。
- **失败可见**：`app/web_search.py` 将异常分为临时错误（超时/连接/限流/5xx，指数退避重试）和
  永久错误（无 key/配额/参数错，直接失败），失败原因写入 `web_error` 返回给用户，不抛异常。
- **异步执行**：RAG 节点全部 async；同步的模型加载、Milvus、BM25 操作通过 `asyncio.to_thread`
  移出事件循环。
- **会话记忆**：`app/memory.py` 持久化"滚动摘要 + 最近 N 轮原文"，支持 SQLite / Redis / 内存
  三种后端，重启不丢（默认 SQLite）。没用 LangGraph checkpointer，因为它每超步都存完整图状态，太重。

## 五、真实失败案例：忠实性检查误杀正确答案

### 5.1 现象

文档原文描述参数规模从 `7 billion` 增长到 `70 billion`，系统生成的中文答案是"从 70 亿增长到 700 亿"。
答案和检索文档一致，但忠实性裁判返回 `no`，链路把正确答案替换为拒答。

这是一个典型的"守门机制自身出错"：检索和生成都正确，最终质量反而被 LLM 裁判拉低。

### 5.2 定位过程

1. **先隔离检索层**：用 `/retrieve` 只执行查询变换、混合检索和精排，不生成答案。返回的原文块正确，排除召回问题。
2. **打开裁判黑盒**：记录评分器原始输出，而不只记录 `yes/no`。日志显示裁判把 `70 billion` 错误理解成 `70 亿`。
3. **做控制变量实验**：保持文档、事实和温度不变，只切换答案语言；英文版本通过、中文换算版本失败，问题收敛到跨语言数量级判断。
4. **确认根因**：不是文档缺失，也不是答案幻觉，而是 LLM 裁判的数学换算错误。

### 5.3 修复

- **减少触发条件**：生成 Prompt 要求数字、单位和专有名词优先原样引用，并保留原文数值。
- **纠正裁判规则**：在 `GROUNDEDNESS_PROMPT` 中加入 `1 billion = 10 亿` 等换算规则及正反例，要求比较前统一单位。
- **增加申诉回环**：新增严格生成 Prompt。第一次判 `no` 时不立即拒答，而是严格重生成一次后再次检查；重试次数有硬上限。
- **防止再次回归**：验收脚本检查换算规则仍存在，并检查 `check_groundedness → generate` 回环可达。

### 5.4 验证证据

| 验证项 | 结果 |
|---|---|
| 图结构与防回归规则 | 运行 `_verify_after_merge.py`，检查 9 节点、条件边、提示词规则齐全 |
| 单元测试 | 运行 `python -m unittest discover -s tests -v`，覆盖联网降级、流式契约、OpenAI 兼容、文档管理、记忆等 |
| 在线端到端与 RAGAs | 仓库提供 `eval_ragas.py`；该项依赖模型/API Key 和网络，应在提交演示前用脱敏评估集重新运行并保存结果，不在本材料中虚构分数 |

Windows PowerShell 下验收脚本含 emoji，建议显式指定 UTF-8，避免 GBK 终端出现与业务无关的 `UnicodeEncodeError`：

```powershell
$env:PYTHONIOENCODING='utf-8'
python _verify_after_merge.py
python -m unittest discover -s tests -v
```

这个案例让我形成了三条可复用经验：先用观测点隔离故障层级；LLM 裁判同样需要监控与回退；
修复不仅要让原用例通过，还要把根因固化成自动化回归检查。
